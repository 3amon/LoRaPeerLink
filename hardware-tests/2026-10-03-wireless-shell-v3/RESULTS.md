# Hardware test results, 2026-10-03

Two Heltec Wireless Shell V3 boards (ESP32-S3 + SX1262)
running `examples/esp32_bench_test`, driven by `hardware-tests/run_bench.py`
for 1 hour 50 minutes. 915 MHz, 125 kHz, 14 dBm; spreading factor per phase.
Board A is `bench-C822`, board B is `bench-341C`.

**The radio link was very weak.** Received signal strength was about -115 dBm
throughout, close to the noise floor, with both boards on one desk; at 0 dBm
nothing got through at all. The boards most likely had no LoRa antennas
attached. Retransmissions and the occasional failed send below are what the
link layer is for on a link like this; with antennas they should be rare.

Across all phases: 1,895 acknowledged pings at normal pace out of 1,901, no
message delivered twice, no corrupted message, no hang, no transmit timeout.

## What this does and does not show

It shows that on real SX1262 radios the link layer (acknowledgments, retries
with backoff, duplicate suppression, the receive queue), RollCall (discovery,
name collision, a node restarting with a new ID), PeerMessenger, the
encrypted link and the continuous-receive `SemtechRadio` driver behave the
way the simulator-based tests say they should, including at SF10 and SF12.

It does not cover: a link with antennas and realistic signal levels, range,
more than two boards, the GPIO0 button, or runs longer than an hour.

## Reproducing

```bash
uv run --with pyserial hardware-tests/run_bench.py hardware-tests/<new dir> /dev/ttyACM0 /dev/ttyACM1
python3 hardware-tests/summarize.py hardware-tests/<new dir>
```

A board that prints `ESP32ChipID=...` and then nothing needs a Heltec license
written to its flash first; see `examples/esp32_bench_test/README.md`.

The raw console logs for each phase are in this directory (`<phase>.log`:
seconds since the phase started, board, console line).
